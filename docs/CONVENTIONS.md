# 저장소 작성 규칙

이 문서는 `custom_skills`에 스킬, 서브에이전트, 슬래시 커맨드를 추가하거나 수정할 때 따르는 규칙이다. 이 저장소를 항상 원본(source of truth)으로 유지하고, 실제 사용 위치인 `~/.claude/`에는 복사본이 아니라 심볼릭 링크를 둔다.

## 1. 디렉터리 구조

```text
custom_skills/
├── README.md
├── docs/
├── skills/
│   └── <name>/
│       ├── SKILL.md
│       ├── references/
│       └── scripts/
├── agents/
│   └── <name>.md
├── commands/
│   └── <name>.md
└── scripts/
    └── install.sh
```

| 위치 | 역할과 규칙 |
| --- | --- |
| `README.md` | 전체 카탈로그와 분류표. 파일 경로를 카테고리별로 중첩하지 말고, README 표에서 용도와 분류를 표현한다. |
| `docs/` | 사람이 읽는 저장소 운영·설치 문서. 스킬 실행에 필요한 지침은 여기에 두지 않는다. |
| `skills/<name>/SKILL.md` | 스킬의 진입점. Claude Code는 `~/.claude/skills/<name>/SKILL.md` 한 단계만 인식하고 하위 카테고리를 중첩 탐색하지 않으므로 `skills/` 바로 아래에 각 스킬을 둔다. `skills/writing/humanize-korean/` 같은 구조는 금지한다. |
| `skills/<name>/references/` | 본문에서 필요할 때 선택적으로 읽을 상세 설명, 규격, 예시, 정책. `SKILL.md`에서 파일과 읽어야 할 조건을 직접 안내한다. |
| `skills/<name>/scripts/` | 반복 실행하거나 결과의 일관성이 중요한 작업을 위한 보조 스크립트. 추가한 스크립트는 대표 입력으로 실제 실행해 검증한다. |
| `agents/<name>.md` | 독립된 컨텍스트와 역할로 위임할 서브에이전트 정의. Claude Code가 로드하려면 `~/.claude/agents/*.md`에 평평하게 있어야 한다. 스킬 폴더 안에 두지 않는다. |
| `commands/<name>.md` | 사용자가 명시적으로 호출하는 슬래시 커맨드 정의. 평평한 파일 목록으로 관리한다. |
| `scripts/install.sh` | 저장소 항목을 `~/.claude/`에 심볼릭 링크하는 설치 도구. 저장소가 원본이므로 파일을 복사하지 않는다. |

`references/`와 `scripts/`는 해당 스킬 내부에 둘 수 있지만, 다른 스킬 폴더를 그 아래에 중첩해서는 안 된다. Claude Code의 인식 방식이 바뀌었다는 공식 근거를 확인하기 전까지 위 배치를 유지한다.

## 2. `SKILL.md` frontmatter 표준

모든 `SKILL.md`는 다음 두 필드를 포함하는 YAML frontmatter로 시작한다.

```yaml
---
name: humanize-korean
description: 한국어 글의 AI 문체를 자연스럽게 윤문한다. 사용자가 "AI 티 없애줘", "사람이 쓴 것처럼 고쳐줘", "번역투 고쳐줘"라고 요청할 때 사용한다.
---
```

### `name`

- 소문자 영문, 숫자, 하이픈만 사용하는 kebab-case로 작성한다.
- 64자 이내의 짧고 구체적인 이름을 권장한다.
- `name` 값과 스킬 폴더 이름을 정확히 일치시킨다.
- 무엇을 다루는지 드러나는 도메인·능력 중심 이름을 우선한다. 예: `humanize-korean`, `postgres-schema-review`.
- `process-data`, `handle-files`처럼 범위가 모호한 동사-목적어 이름은 지양한다. 특정 행동 자체가 스킬의 경계를 정확히 나타낼 때만 동사형을 쓴다.
- `helper`, `utils`, `general`처럼 다른 스킬과 구분되지 않는 이름은 쓰지 않는다.

### `description`

`description`은 단순 소개문이 아니라 스킬 발동을 결정하는 핵심 메타데이터다. 본문은 발동된 뒤에야 읽히므로, **사용자가 실제로 말할 트리거 문구와 적용 상황을 반드시 `description`에 넣는다.**

- 첫 문장에는 스킬이 무엇을 처리하고 어떤 결과를 내는지 쓴다.
- 이어서 대표 요청 문구, 파일 형식, 도구, 업무 상황 등 구체적인 발동 조건을 쓴다.
- 같은 뜻의 표현 중 실제 사용 가능성이 높은 문구를 3~8개 정도 선별한다. 가능한 모든 동의어를 나열하지 않는다.
- 다만 한국어와 영어를 섞어 쓰는 스킬은 각 언어에서 실제로 쓰는 표현을 따로 넣는다. "커밋해줘"만 넣으면 "commit"에 걸리지 않는다. 이때는 언어별로 3~8개씩 잡는다.
- 발동해야 하는 예와 발동하면 안 되는 경계를 설명할 필요가 있으면 짧게 포함한다.
- `문서 작업`, `글쓰기`, `코드 수정`처럼 지나치게 넓은 트리거는 피한다. 범위가 넓으면 관련 없는 요청을 가로채 다른 스킬의 발동을 방해할 수 있다.
- 새 description은 대표 발동 예와 비발동 예를 각각 준비해 실제 사용에서 경계를 점검한다.

이 저장소에서는 `name`, `description`을 필수 기본 필드로 사용한다. 다른 필드가 필요하면 실제 로딩 테스트로 지원 여부를 먼저 확인한다.

`version` 필드는 실제로 확인됐다. `humanize-korean`이 `version: "1.5.0"`을 frontmatter에 두고 있으며 이 상태로 정상 로드된다. 즉 인식되지 않는 추가 필드가 있어도 로딩이 깨지지는 않는다. 다만 그 값을 Claude Code가 해석해 준다는 보장은 없으므로, 버전은 frontmatter에 두든 본문에 두든 **사람과 문서가 읽는 값**으로 취급한다.

## 3. 무엇으로 만들지 판단하기

| 형태 | 선택 기준 | 적합한 예 |
| --- | --- | --- |
| 스킬 | 요청 내용에 따라 자동으로 발동해야 하고, 반복 가능한 지식·절차·스크립트가 필요할 때 | 특정 문체 윤문, 특정 API 작업 절차, 파일 형식 처리 |
| 서브에이전트 | 주 작업과 컨텍스트를 분리해 전문 역할에 위임하거나, 독립적인 조사·검토 결과가 필요할 때 | 보안 검토자, 코드 리뷰어, 조사 전담 에이전트 |
| 슬래시 커맨드 | 자동 발동보다 사용자가 호출 시점과 동작을 명시적으로 통제해야 하며, 비교적 고정된 프롬프트 절차를 반복할 때 | `/release-note`, `/daily-review` 같은 수동 실행 작업 |

다음 순서로 판단한다.

1. 사용자가 이름을 직접 호출해야 안전하거나 예측 가능한가? 그렇다면 슬래시 커맨드를 우선한다.
2. 독립 컨텍스트, 별도 역할, 병렬 또는 위임 실행이 핵심인가? 그렇다면 서브에이전트를 우선한다.
3. 자연어 요청을 감지해 재사용 지침과 자료를 불러오는 것이 핵심인가? 그렇다면 스킬로 만든다.
4. 두 형태가 모두 필요하면 책임을 나눈다. 예를 들어 스킬은 도메인 지식을 제공하고, 커맨드는 사용자가 시작하는 고정 워크플로를 제공한다. 같은 긴 지침을 양쪽에 복제하지 않는다.

## 4. `SKILL.md` 분량과 분리 기준

- 본문에는 핵심 절차, 의사결정 기준, 안전 제약, 리소스를 읽는 조건만 둔다.
- 평소에는 300줄 안팎을 목표로 하고, **400줄에 가까워지면 분리를 검토하며 500줄을 넘기지 않는다.**
- 상세 API 규격, 긴 예시 모음, 도메인 정책, 스키마, 변형별 설명은 `references/`로 옮긴다.
- 반복해서 작성하는 코드이거나 실행 결과의 일관성이 중요하면 설명을 늘리는 대신 `scripts/`로 만든다.
- 핵심 지침과 reference에 같은 내용을 중복하지 않는다. `SKILL.md`에는 reference 링크와 "언제 읽을지"만 명확히 적는다.
- reference는 가능하면 `SKILL.md`에서 한 단계로 직접 연결한다. reference가 다른 reference를 연쇄적으로 찾아가게 만들지 않는다.
- 100줄이 넘는 reference에는 문서 앞부분에 목차를 둔다. 10,000단어가 넘는 자료는 `SKILL.md`에 검색할 키워드나 구간을 안내한다.

## 5. 버전과 변경 이력

기존 `humanize-korean`이 `v1.6.1`까지 발전한 전례처럼, 동작이나 발동 범위가 바뀌는 스킬은 [Semantic Versioning](https://semver.org/lang/ko/) 형식 `vMAJOR.MINOR.PATCH`로 관리한다.

- `PATCH`: 오탈자, 표현 명료화, 결과를 바꾸지 않는 작은 수정, 버그 수정.
- `MINOR`: 하위 호환되는 트리거·절차·예시·리소스 추가 또는 품질 개선.
- `MAJOR`: 기존 사용법과 호환되지 않는 구조 변경, 트리거 의미의 큰 변경, 출력 계약 변경.
- 실험 중인 최초 버전은 `v0.x.y`, 안정적으로 쓰기 시작한 스킬은 `v1.0.0`부터 시작한다.
- 버전 표기 위치는 두 가지가 공존한다. `humanize-korean`처럼 frontmatter `version` 필드를 쓰는 방식과, `SKILL.md` 본문에 `버전: vX.Y.Z`를 적는 방식 모두 동작한다. 새 스킬은 본문 표기를 기본으로 하되, 기존 스킬의 방식을 억지로 바꾸지 않는다.
- 어느 방식이든 **frontmatter와 본문의 버전이 서로 어긋나지 않게** 한다. 한쪽만 올리는 실수가 가장 흔하다.
- 사소한 수정이라도 동작, 트리거, 의존성, 출력 형식에 영향이 있으면 변경 이력을 남긴다.
- 변경 이력은 해당 스킬의 `references/CHANGELOG.md`에 최신 버전부터 역순으로 기록한다. 각 항목에는 날짜(`YYYY-MM-DD`), 버전, 사용자에게 의미 있는 변경점을 적고 커밋 해시나 작업 과정은 생략한다.
- 변경 이력이 짧은 초기 스킬은 `SKILL.md` 끝에 최근 항목만 둘 수 있다. 이력이 5개를 넘거나 본문 가독성을 해치면 `references/CHANGELOG.md`로 분리하고 `SKILL.md`에서 링크한다.
- 저장소 전체에 영향을 주는 설치 방식이나 공통 규칙 변경은 개별 스킬 CHANGELOG가 아니라 관련 `docs/` 문서에서 설명한다.

## 6. 새 스킬 추가 체크리스트

- [ ] 스킬과 비슷한 기존 항목이 없는지 README 카탈로그를 확인했다.
- [ ] 스킬, 서브에이전트, 슬래시 커맨드 중 적절한 형태인지 판단했다.
- [ ] `skills/<name>/SKILL.md` 한 단계 구조로 만들었다.
- [ ] 폴더명과 frontmatter의 `name`이 일치하며 kebab-case 규칙을 지킨다.
- [ ] frontmatter에 `name`과 `description`이 있고 YAML 문법이 올바르다.
- [ ] `description`에 구체적인 트리거 문구와 적용 범위를 넣었다.
- [ ] 대표 발동 예와 비발동 예로 다른 스킬을 가로채지 않는지 점검했다.
- [ ] 본문이 500줄 미만이며 상세 자료를 `references/`로 적절히 분리했다.
- [ ] reference 링크와 읽는 조건이 `SKILL.md`에 명시되어 있다.
- [ ] 보조 스크립트를 실제로 실행해 대표 입력과 실패 입력을 검증했다.
- [ ] 버전과 필요한 변경 이력을 기록했다.
- [ ] `README.md` 카탈로그 표에 스킬 이름, 설명, 경로를 추가하고 분류를 갱신했다.
- [ ] `scripts/install.sh` 실행 후 링크와 Claude Code에서의 발동을 확인했다.
- [ ] 저장소가 원본이고 `~/.claude/skills/<name>`이 심볼릭 링크인지 확인했다.
